# Dependency baseline

This document defines the dependency, security, build, and distribution policy for `mivama-digital/media-folders`.

## Runtime contracts

- Node.js: `>=24 <25`
- npm: `>=11 <12`
- PHP: `>=8.3`
- WordPress: `>=6.8`
- JavaScript lockfile: `package-lock.json` (`lockfileVersion: 3`)
- PHP lockfile: `composer.lock`
- npm package manager: `npm@11.17.0`
- `.npmrc`: `engine-strict=true` and `strict-allow-scripts=true`

Dependency rules:

- no floating `latest` or `*` versions;
- no routine `npm audit fix --force`;
- no `--legacy-peer-deps` bypasses;
- no unexplained dependency overrides;
- major dependency upgrades stay isolated from feature work;
- lockfiles are generated by their package managers, never hand-edited;
- every dependency change must pass the full security, test, build, SBOM, and release-archive pipeline.

- Webpack + webpack-cli;

- full npm audit: `0` vulnerabilities;

The previous WordPress meta-tooling graph contained 32 npm findings (`10 high`, `21 moderate`, `1 low`). The focused graph reaches zero without forced audit fixes, blanket overrides, or legacy peer-resolution bypasses.

## WordPress JavaScript host boundary

WordPress-hosted framework packages are not duplicated unnecessarily.

`@wordpress/components` is intentionally not installed as a direct npm runtime dependency. Production imports are externalized to the `wp-components` WordPress handle. Vitest uses a small test-only adapter instead of reinstalling the Components dependency graph.

Vitest also uses explicit host adapters for:

- `@wordpress/compose`;
- `@wordpress/hooks`;
- `@wordpress/url`.

Installed packages such as `@wordpress/element`, `@wordpress/i18n`, `@wordpress/api-fetch`, `@wordpress/data`, and `@wordpress/icons` continue to use their real npm modules during tests. `@wordpress/icons` remains installed because icons are bundled by the current production build rather than externalized.

## Reviewed npm install scripts

## PHP runtime boundary

The activated WordPress plugin has **no third-party PHP runtime library dependency**.

`composer/installers` remains in `composer.json` because the repository is a `wordpress-plugin` Composer package and the installer preserves the expected installation behavior for Composer/VCS consumers. It is installation tooling, not code required by WordPress after the plugin is installed.

Production runtime classes are loaded through the repository-owned `autoload.php`, which maps the `VirtualMediaFolders\\` namespace to `src/`.

`npm run check:php-runtime-autoload` runs a standalone PHP smoke check that:

- does not require Composer's autoloader;
- resolves every core plugin PHP class;
- fails if any `/vendor/` file is included.

Composer is still used in development for PHPUnit, Brain Monkey, lockfile validation, and security auditing.

## Vendor-free WordPress distribution

The installable WordPress ZIP intentionally contains no Composer runtime tree.

`.distignore` excludes:

- `vendor/`;
- `composer.json`;
- `composer.lock`;
- npm package-manager files;
- tests, scripts, security metadata, internal docs, and other repository-only files.

The ZIP builder requires:

- `virtual-media-folders.php`;
- `autoload.php`;
- `readme.txt`;
- `LICENSE`;
- production build assets.

It fails if `vendor/` or Composer package-manager metadata leaks into the archive.

Release and WordPress.org workflows therefore do **not** run `composer install --no-dev` before packaging. They run the normal development Composer install only where tests require it; `.distignore` guarantees that development vendor code cannot enter the distributable plugin.

## Composer SBOM policy

The Composer CycloneDX artifact describes **shipped PHP runtime code**, not every repository installation tool.

`composer/installers` is deliberately excluded from the runtime SBOM because it is not distributed in the WordPress ZIP. With the current core plugin dependency graph, the Composer runtime SBOM contains zero third-party components.

CI fails if a PHP runtime component appears without the distribution policy being updated deliberately. If a real PHP runtime library is added later, all of the following must change together:

1. Composer dependency declaration;
2. runtime autoload/distribution strategy;
3. GPL compatibility review;
4. runtime SBOM expectation;
5. release ZIP validation;
6. security/audit policy.

## License policy

The repository and plugin are `GPL-2.0-or-later`.

`npm run check:licenses` begins with direct production npm dependencies and walks reachable `dependencies` and `optionalDependencies`. Development tooling and WordPress host peer contracts are not mislabeled as distributed plugin runtime dependencies.

New distributed dependencies must be technically justified and GPLv2-compatible.

## WordPress.org deployment contract

The GitHub repository is `media-folders`, while the existing plugin/SVN slug remains `virtual-media-folders`.

WordPress.org deployment is manual and confirmation-gated. The workflow:

- checks out an explicit release tag;
- derives and validates the SVN version from that tag;
- runs the same dependency/security/test/build gates;
- verifies the vendor-free PHP runtime;
- uses the explicit `virtual-media-folders` slug;
- defaults to dry-run mode;
- requires authorized WordPress.org credentials for a real commit.

Creating a Git tag alone never deploys to WordPress.org.

## Repository security prerequisite

GitHub Dependency Review requires the repository Dependency Graph. Until it is enabled under repository Code Security settings, the CI job reports the prerequisite and skips the blocking dependency-review action.
